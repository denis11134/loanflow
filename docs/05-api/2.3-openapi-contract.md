# 2.3. API и OpenAPI-контракт

**Статус:** согласовано для учебного стенда.

- `api/loanflow.openapi.yaml` — операции МП и рабочих мест.
- `api/abs.openapi.yaml` — отдельный служебный интерфейс учебной АБС.

Оба контракта описаны в [OpenAPI 3.0.3](https://spec.openapis.org/oas/v3.0.3.html). Источники поведения — [требования 1.6](../03-requirements/1.6-mvp-requirements.md), [статусная модель v3](../02-processes/1.5-status-model.md), [модель данных](../04-data/2.1-logical-er-model.md), [схема PostgreSQL](../04-data/2.2-physical-model-postgresql.md) и [контракт учебной АБС](../06-integrations/abs-contract.md). [Прототип](../08-prototypes/index.md) помогает сверить действия и видимость данных по ролям.

## Операции и покрытие сценариев

| Сценарий | Операции API | Что проверить |
|---|---|---|
| UC-01 · Подписание и выдача | Начать попытку, запросить SMS, передать код, прочитать попытку и Договор, отказаться через МП или КЦ | Сроки и повтор запроса, различие ожидания и окончательного итога, доступность отказа в охлаждении |
| UC-02 · Подача | Создать, обновить, открыть и подать черновик, отменить Заявку | Частичный черновик, подтверждение исходной подачи при повторе, блокирующая Заявка или Договор |
| UC-03 · Оценка | Прочитать свою Заявку | Видимые переходы, нейтральный отказ, отдельное сообщение о самозапрете и отсутствии согласия |
| UC-04 · Ручное рассмотрение | Очередь, карточка, ручное решение, эскалации, недельный отчёт | Допустимость роли, первое зафиксированное решение, сохранение исхода после повтора |
| UC-05 · Предложение и ИУ | Прочитать состояние Предложения, получить экземпляр ИУ, подтвердить показ предупреждения | ИУ готовятся или предоставлены, тот же документ и дедлайн при повторе, версия предупреждения |
| UC-06 · Просмотр | Своё состояние в МП, статус в КЦ, проверка наличия в отделении | Чужие данные скрыты, отрицательный результат отличается от недоступности проверки |
| UC-07 · Сверка | Очередь, карточка, регистрация чтения и получение его результата, принятие или повтор закрытия | Допуск по последнему зарегистрированному чтению, повтор принятой команды, возврат сохранённого финального результата |

Автоматическая оценка, публикация ИУ, таймеры, запуск выдачи и воркер outbox выполняются внутри LoanFlow. Их результаты наблюдаются через чтение Заявки, Предложения, попытки, Договора или сверки. Схемы не включают банковские каналы и проверки, которые остаются открытыми в 1.6.

## Решения для учебного стенда

### Доступ и идентификация

Токен стенда передаётся как Bearer. LoanFlow получает из доверенного контекста роль и личность, для МП — также `customer_id`, сессию и устройство. МП открывает только собственные записи. Входные идентификаторы обозначают ресурс, но не подтверждают личность. Для недоступного чужого ресурса API возвращает тот же `404`, что и для отсутствующего.

КЦ и отделение используют синтетический `customer_id` как ключ поиска. Оператор КЦ с действующими полномочиями может посмотреть статус до идентификации клиента. Просмотр КЦ показывает только статусы и сроки, без причины отказа, балла скоринга или счёта. Отделение получает два признака наличия, включая действующий Договор из тестового набора Legacy. Ошибка проверки возвращается как `503`.

Для отказа через КЦ LoanFlow выдаёт непрозрачный `X-Identification-Token` на пять минут по результату имитации идентификации в доверенном контексте звонка. Подтверждение связано с оператором, его сессией, клиентом и Договором. Новая команда отказа требует действительного подтверждения и `COOLING_OFF`. После запуска выдачи попытка отказа даёт `409 WITHDRAWAL_UNAVAILABLE` с текущим статусом Договора.

Действия `EDIT_DRAFT` и `SUBMIT` относятся только к `DRAFT`. Отмена Заявки допустима из `DRAFT`, `SCORING`, `UNDERWRITING` и `APPROVED`. У отменённого черновика `submitted_at` остаётся `null`. У `SCORING` указан момент подачи, у `CONTRACT_SIGNED` — идентификатор Договора. `OPEN_TERMS` относится к опубликованным ИУ. Для `START_SIGNING` нужны `APPROVED`, доступные ИУ, действующий срок, отсутствие активной попытки и подтверждение показа предупреждения при его обязательности. Проверки срока, показа и полномочий выполняет сервис.

### Повторы и состояние проверки ПЭП

| Команда | Поведение после потери ответа |
|---|---|
| Создание или редактирование черновика, старт попытки, повторное SMS, проверка ПЭП, ручное решение, отказ через КЦ, регистрация чтения АБС | Повтор с тем же `Idempotency-Key` возвращает код и результат первоначальной принятой команды. Например, сохраняются `attempt_id`, номер повторной отправки или `read_seq`. Другой запрос под тем же ключом даёт `409 IDEMPOTENCY_KEY_REUSED`. |
| Подача Заявки | Повтор возвращает исходный `202` с `application_id`, временем подачи и `accepted_status: SCORING`. Текущий статус запрашивается отдельно. |
| Отмена Заявки или отказ через МП | Повтор для уже отменённой записи возвращает тот же результат без повторного освобождения резерва. |
| Повтор отказа через КЦ | Принятая команда возвращает сохранённый результат для той же авторизованной сессии, ключа и подтверждения. Истечение подтверждения после принятия команды не мешает получить этот результат. |
| Повтор принятого закрытия | Уполномоченный оператор повторяет ту же команду по исходному `instruction_id`. Если итог уже сохранён, LoanFlow возвращает `200` с ним. Если итог ещё неизвестен, возвращает `202` и может повторить вызов закрытия в АБС. |

Запись принятой команды с ключом сохраняется вместе с её эффектом или регистрацией задания. Ключ ограничен личностью, ролью, методом и путём. Записи повторов хранятся до сброса учебного стенда. Сопоставление запроса использует отпечаток, защищённый ключом сервиса. Исходный SMS-код, токены и полные тела запросов в журнал повторов не записываются. Проверка полномочий применяется и к повтору. Хранение ответов на ключи относится к реализации сервиса и её миграции.

При успешном приёме запроса проверки ПЭП API возвращает `202`, а итог клиент читает по `attempt_id`. `VERIFYING` означает принятую проверку с неизвестным исходом. В этом состоянии новый ввод, повторное SMS и новая попытка недоступны. `CLOSED` содержит причину, в том числе `ATTEMPT_EXPIRED` или `OFFER_EXPIRED`. Для отклонённой до принятия команды сроки также различаются кодами `SIGNING_ATTEMPT_EXPIRED` и `OFFER_EXPIRED`. При истечении обоих сроков приоритет у истечения Предложения. Сетевая ошибка или `503` сама по себе не устанавливает исход. Клиент может прочитать текущее состояние или повторить запрос с исходным ключом.

В `VERIFYING`, `SIGNED` и `CLOSED` оба флага действий ПЭП выключены. В `OPEN` повтор SMS недоступен при нуле оставшихся отправок. Повторное SMS передаёт тот же код для той же попытки до её исходного дедлайна. Доступны два повтора. Повтор принятой команды с исходным ключом возвращает прежний результат и не меняет счётчик.

После `202` сервис возобновляет исходную проверку по тому же `attempt_id` без нового действия клиента. Для этого вместе с принятием команды сохраняются защищённые данные, достаточные для восстановления. Исходный код и токены исключены из журнала повторов и диагностики. При неопределённом результате сохраняется `VERIFYING` до ответа или ближайшего дедлайна. Своевременная проверка под блокировкой сохраняет право на коммит. Поздний результат закрытой попытки не меняет Договор.

### Ручная сверка и учебная АБС

Оператор получает `instruction_id` из очереди сверки и видит в карточке последнее зарегистрированное чтение, наличие сохранённой команды, доступность нового закрытия и повтора. Новое чтение регистрируется до вызова АБС. Повтор того же запроса чтения возвращает первоначальный номер, намеренное новое чтение получает новый номер. Для допуска закрытия используется максимальный зарегистрированный `read_seq`, независимо от порядка прихода ответов.

Первое закрытие требует явной команды в `DISBURSEMENT_PROCESSING` после `NOT_FOUND` или `PENDING` последнего зарегистрированного чтения, если команда ещё не принята. Принятая команда коммитится до вызова АБС. Любой уполномоченный оператор сверки может повторить её по тому же идентификатору, пока Договор в обработке, независимо от нового чтения. После `POSTED` или `CLOSED` авторизованный запрос закрытия возвращает уже сохранённый итог без нового вызова АБС. Карточка доступна по идентификатору после завершения с обоими флагами закрытия `false`. Схема проверяет сочетания полей карточки. Сервис проверяет права, принадлежность распоряжения и максимальный `read_seq`.

Для незавершённого чтения окно восстановления составляет 10 секунд с регистрации. Внутри окна сервис возобновляет исходное чтение с тем же `read_seq`. Таймаут вызова ограничен меньшим из 2 секунд и остатка окна. При таймауте вызова или истечении окна без сохранённого ответа сервис фиксирует `TIMEOUT`. Поздний неопределённый ответ не переписывает `TIMEOUT` и не разрешает первое закрытие. Корректный подтверждённый `POSTED` или `CLOSED` можно применить к Договору, который ещё в обработке, по правилам корреляции и однократного изменения резерва.

В служебном API идентификатор распоряжения передаётся в пути и возвращается в каждом протокольном ответе. `NOT_FOUND` возвращается как бизнес-состояние с HTTP 200. Если АБС не может подтвердить согласованное состояние, чтение возвращает `409 READ_CONFLICT`. При совпавшем идентификаторе LoanFlow фиксирует `CONFLICT` и требует нового разрешающего чтения для первой команды закрытия. Повтор отправки с изменёнными реквизитами даёт `409 REQUISITES_CONFLICT`. `POSTED` содержит реквизиты проводки, `CLOSED` — только идентификатор и состояние. LoanFlow сопоставляет ответ с исходным распоряжением. При ошибке корреляции результат не применяется и резерв остаётся удержанным. После коммита начала отправки автоматический повтор отправки не выполняется.

### Предоставление ИУ и предупреждение о ПДН

Первое предоставление ИУ — коммит публикации неизменяемого экземпляра, с которого он доступен авторизованному МП. В этой операции сохраняются экземпляр, момент предоставления и дедлайн на пятую следующую рабочую дату с сохранением местного времени публикации по [календарю стенда](../03-requirements/1.6-mvp-requirements.md#stand-calendar). Для обязательной операции публикации действует [политика повторов](../03-requirements/1.6-mvp-requirements.md#stand-retries). Запросы чтения срок не меняют. МП получает метаданные в JSON, а неизменяемый документ — отдельным ответом `application/pdf`. Хеш в метаданных относится к точным байтам этого PDF.

Когда предупреждение обязательно, МП показывает текст и подтверждает его показ с актуальной версией. LoanFlow фиксирует первый серверный момент подтверждения для экземпляра ИУ. Повтор возвращает тот же момент. При обязательном предупреждении старт Подписания требует зафиксированного показа.

### Данные андеррайтинга и представление значений

Пилотные андеррайтеры видят общую очередь `UNDERWRITING`. Минимальная карточка содержит идентификатор Заявки, запрошенные сумму и срок, момент подачи, дедлайн SLA и факт эскалации. Доступ к расширенным данным карточки остаётся отдельным вопросом банковского сценария. Руководитель пилотной группы читает эскалации и недельный отчёт. Для отчёта задаются понедельник отчётной недели и момент среза не раньше окончания этой недели в тестовом часовом поясе.

В результате ручного решения `REJECT` соответствует `REJECTED` и `BANK_REJECTED`. Переданный код причины сохраняется. Для отказа после `APPROVE` по ПСК или квоте код причины обязателен. При одобрении результат и статус — `APPROVED`, поле причины отсутствует. Повтор с исходным ключом возвращает первоначальный результат команды.

Положительная сумма в пяти полях запроса и ответа (`DraftInput`, `DraftPatch`, `ApplicationView`, `TermsAvailable`, `UnderwritingView`) имеет диапазон от `1` до `9223372036854775807` копеек включительно. Сервис проверяет этот диапазон точным сравнением целых чисел.

JSON для МП и рабочих мест передаёт суммы в копейках и точные десятичные значения ПСК строками. Служебный API АБС передаёт `amount_minor` целым числом в диапазоне PostgreSQL `bigint`. Моменты времени передаются с явным смещением. Доли в отчёте представлены числами от 0 до 1. При пустом знаменателе соответствующая доля равна `null`, интерфейс показывает «Нет данных».
