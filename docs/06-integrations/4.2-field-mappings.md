# 4.2. Маппинги полей

Контракты описывают будущие учебные интеграции 4.3. Все три заглушки ищут клиента по синтетическому UUID. Форматы REST заданы в `api/checks.openapi.yaml`, элементы SOAP — в `api/passport.xsd`.

## Порядок проверок

1. При `AML Block` действует текущий отказ. После `AML Pass` LoanFlow проверяет паспорт. Вердикт `INVALID` даёт `BANK_REJECTED` с внутренним кодом `PASSPORT_INVALID` и нейтральным сообщением в МП.
2. После `VALID` LoanFlow проверяет согласие. Непустая `consent_ref` в версии профиля, зафиксированной при подаче, означает действующее учебное согласие. Если ссылки нет, действует отказ `CREDIT_REPORT_CONSENT_REQUIRED`. Иначе LoanFlow запрашивает КБКИ одним вызовом. При применимом самозапрете действует отказ `SELF_BAN`.
3. Если самозапрета нет, LoanFlow проверяет полноту и корректность платежей из КБКИ и дохода из зафиксированного профиля. Например, сочетание пропущенного поля платежей и дохода `null` даёт `SYSTEM_ERROR`. При корректных платежах и доходе `null` или `0` действует отказ `NO_CONFIRMED_INCOME`. Антифрод вызывается после этих проверок.
4. При `CLEAR` LoanFlow выполняет расчёты и скоринг по 3.3. При `SUSPECTED` после успешного расчёта графика, ПДН и ПСК LoanFlow сохраняет условия и направляет заявку в `UNDERWRITING` независимо от скорингового порога. Ручной `APPROVE` проверяет предел ПСК и квоту по сохранённым условиям. При ошибке обязательного расчёта действует `SYSTEM_ERROR`.

Переход по результату оценки применим только пока заявка в `SCORING`. [Расчёты 3.3](../03-requirements/3.3-calculation-tasks.md) · [Требования MVP](../03-requirements/1.6-mvp-requirements.md)

## КБКИ

`POST /credit-reports`, запрос и ответ `application/json`.

| Поле | Где | Формат | Источник и использование |
|---|---|---|---|
| `customer_id` | Запрос и ответ | UUID, обязательно | LoanFlow берёт из заявки, заглушка возвращает тот же UUID. |
| `consent_ref` | Запрос | Строка с непробельным символом, обязательно | Ссылка из зафиксированного профиля, передаётся без преобразования. |
| `self_ban_applies` | Ответ `200` | Булево значение, обязательно | Из тестового набора КБКИ. Сохраняется в `evaluation.self_ban_applies`. При `true` ответ состоит из этого признака и UUID клиента. |
| `credit_report_ref` | Ответ `200` при `false` | Строка с непробельным символом, обязательно | Ссылка из тестового набора КБКИ. Сохраняется в `evaluation.credit_report_ref`. |
| `existing_payments_rub` | Ответ `200` при `false` | Неотрицательная десятичная строка с двумя знаками после точки, обязательно | Рубли в месяц из тестового набора КБКИ. Преобразуются в точное десятичное число и сохраняются в `evaluation.monthly_existing_payments_rub`. При отсутствии текущих платежей передаётся `"0.00"`. |

Для ПДН к платежам из КБКИ прибавляется регулярный месячный платёж нового кредита. В знаменателе используется `payroll_income_rub` из зафиксированного профиля.

Запрос

```json
{"customer_id":"10000000-0000-0000-0000-000000000001","consent_ref":"stand-consent-1"}
```

Ответ `200`

```json
{"customer_id":"10000000-0000-0000-0000-000000000001","self_ban_applies":false,"credit_report_ref":"stand-report-1","existing_payments_rub":"25000.00"}
```

## Паспорт

`POST /passport-check`, SOAP 1.1, `Content-Type: text/xml; charset=utf-8`. В запросе используется `SOAPAction: "urn:loanflow:training:passport:v1#CheckPassport"`. SOAP Body содержит ровно один элемент операции.

| Поле | Где | Формат | Источник и использование |
|---|---|---|---|
| `customer_id` | Запрос и ответ | UUID, обязательно | LoanFlow берёт из заявки, заглушка возвращает тот же UUID. |
| `verdict` | Ответ `200` | `VALID` или `INVALID`, обязательно | Значение из тестового набора паспортной проверки. При `VALID` LoanFlow продолжает оценку. |

Запрос

```xml
<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/"
               xmlns:p="urn:loanflow:training:passport:v1">
  <soap:Body>
    <p:CheckPassportRequest>
      <p:customer_id>10000000-0000-0000-0000-000000000001</p:customer_id>
    </p:CheckPassportRequest>
  </soap:Body>
</soap:Envelope>
```

Ответ `200`

```xml
<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/"
               xmlns:p="urn:loanflow:training:passport:v1">
  <soap:Body>
    <p:CheckPassportResponse>
      <p:customer_id>10000000-0000-0000-0000-000000000001</p:customer_id>
      <p:verdict>VALID</p:verdict>
    </p:CheckPassportResponse>
  </soap:Body>
</soap:Envelope>
```

## Антифрод

`POST /fraud-checks`, запрос и ответ `application/json`.

| Поле | Где | Формат | Источник и использование |
|---|---|---|---|
| `customer_id` | Запрос и ответ | UUID, обязательно | LoanFlow берёт из заявки, заглушка возвращает тот же UUID. |
| `verdict` | Ответ `200` | `CLEAR` или `SUSPECTED`, обязательно | Из тестового набора антифрода. `CLEAR` сохраняет обычный путь скоринга. `SUSPECTED` требует ручного решения. |

Запрос

```json
{"customer_id":"10000000-0000-0000-0000-000000000001"}
```

Ответ `200`

```json
{"customer_id":"10000000-0000-0000-0000-000000000001","verdict":"SUSPECTED"}
```

## Ответы и сбои

Во всех трёх интеграциях бизнес-результат передаётся в корректном ответе `200`. LoanFlow проверяет формат и совпадение UUID клиента перед применением результата.

| Случай | REST | SOAP | Действие LoanFlow |
|---|---|---|---|
| Некорректный запрос или неизвестный клиент | `400` или `404` соответственно | `500` с SOAP Fault `soap:Client` | `SYSTEM_ERROR` сразу |
| Нарушение формата ответа или несовпадение UUID | Например, `200` без текущих платежей при `self_ban_applies=false` | Например, `200` без `verdict` | `SYSTEM_ERROR` сразу |
| Временная недоступность | `503`, таймаут или транспортный сбой | `503`, таймаут или транспортный сбой | До трёх попыток всего с таймаутом 2 секунды и паузами 1 и 3 секунды. При исчерпании попыток — `SYSTEM_ERROR`. |

Для классификации HTTP `503` тело ответа не требуется. Остальные ответы вне контракта считаются постоянной технической ошибкой. [Правила повторов](../03-requirements/1.6-mvp-requirements.md#stand-retries)

## АБС

`PUT /instructions/{instruction_id}` отправляет распоряжение, `GET /instructions/{instruction_id}` читает состояние, `PUT /instructions/{instruction_id}/closure` закрывает распоряжение. Идентификатор один для всех трёх операций. Чтение и закрытие идут без тела запроса.

| Поле | Где | Формат | Источник и использование |
|---|---|---|---|
| `instruction_id` | Путь и протокольные ответы | UUID, обязательно | LoanFlow генерирует при создании распоряжения и сверяет с ним ответ. |
| `account_ref` | Отправка и `POSTED` | Непустая строка, обязательно | Счёт из договора. |
| `amount_minor` | Отправка и `POSTED` | Положительное целое `int64`, обязательно | Сумма предложения в копейках. |
| `currency` | Отправка и `POSTED` | `RUB`, обязательно | Фиксируется при создании распоряжения. |
| `state` | Ответ `200` | Строка, обязательно | Отправка допускает `PENDING`, `POSTED` и `CLOSED`. Чтение также допускает `NOT_FOUND`. Закрытие возвращает `POSTED` или `CLOSED`. |
| `posting_ref` | `POSTED` | Непустая строка, обязательно | Идентификатор проводки из АБС, сохраняется с итогом. |
| `posted_at` | `POSTED` | Дата и время с явным смещением, обязательно | Время зачисления из АБС, используется в статусе договора. |

LoanFlow применяет корректный `POSTED` или `CLOSED` к договору в `DISBURSEMENT_PROCESSING`. Для `POSTED` дополнительно сверяются счёт, сумма и валюта. В `CLOSED` присутствуют только `instruction_id` и `state`. При неизвестном итоге договор остаётся в обработке, резерв удерживается.
