# 5.4. Оркестрация оценки в Camunda

В [5.1](5.1-service-decomposition.md) определена граница сервиса оценки, а в
[5.2](5.2-assessment-events.md) — обмен запросом и результатом через Kafka.
В этой главе Camunda управляет последовательностью этапов и ожиданиями внутри
сервиса оценки. Ядро LoanFlow по-прежнему принимает кредитное решение и владеет
бизнес-статусами заявки.

Исполняемый исходник —
[`diagrams/loanflow-assessment.bpmn`](https://github.com/denis11134/loanflow/blob/main/diagrams/loanflow-assessment.bpmn).
Идентификатор процесса — `loanflow-assessment`. Файл содержит BPMN DI с координатами
элементов для открытия в Camunda Modeler.

## Граница изменений

Camunda заменяет планирование этапов оценки через `assessment_task.run_at`.
Последовательность остаётся прежней: AML → паспорт и согласие → КБКИ и проверка входов ПДН →
антифрод и расчёт условий → DE. Бизнес-отказ или технический исход могут завершить
каскад раньше DE.

Снимок подачи, входы, промежуточные расчёты и итог оценки хранятся в отдельной
PostgreSQL сервиса оценки. Ядро принимает `AssessmentCompleted` через прежний
результирующий топик и применяет его только к исходной подаче в `SCORING`.
Андеррайтер продолжает работать через существующий API. Таймеры предложения,
подписания и периода охлаждения, резерв, выдача и сверка с АБС остаются в ядре.

## Исполняемый процесс

None start event ведёт в задачу регистрации экземпляра. Регистрация связывает
`processInstanceKey` с записью `assessment_task`. Только закреплённый за записью
экземпляр вправе выполнять этапы; лишний экземпляр завершается до проверок.

При создании экземпляра `businessId` составляется как
`<application_id>:<submitted_at>`: UUID заявки и момент исходной подачи, разделённые
двоеточием. Camunda ограничивает уникальность этого идентификатора среди активных
экземпляров. После завершения экземпляра такое ограничение больше не защищает от
повторного запуска; постоянная привязка владельца в PostgreSQL сохраняет правило
одной оценки исходной подачи и отклоняет лишний экземпляр на регистрации.

| Задача BPMN | Тип задания Camunda | Назначение |
|---|---|---|
| `Task_REGISTER` | `loanflow-assessment-register` | Закрепить экземпляр за оценкой |
| `Task_AML` | `loanflow-assessment-AML` | Выполнить AML |
| `Task_PASSPORT` | `loanflow-assessment-PASSPORT` | Проверить паспорт и согласие |
| `Task_CREDIT_REPORT` | `loanflow-assessment-CREDIT_REPORT` | Получить КБКИ, проверить самозапрет и входы ПДН |
| `Task_FRAUD` | `loanflow-assessment-FRAUD` | Проверить антифрод, рассчитать условия и скоринг |
| `Task_DE` | `loanflow-assessment-DE` | Подготовить рекомендацию DE |
| `Task_FINALIZE` | `loanflow-assessment-finalize` | Зафиксировать результат и задание его публикации |

Воркер получает бизнес-данные из своей PostgreSQL по `assessmentId`. В движок
передаются только `assessmentId`, `route` и `waitDuration`. Финансовые условия,
доход, платежи, согласие, идентификатор клиента и содержимое проверок в переменные
процесса не копируются.

| `route` | Переход после этапа |
|---|---|
| `NEXT` | Следующий этап каскада; после DE — финализация |
| `FINISH` | Финализация подготовленного результата |
| `STOP` | Завершение экземпляра без публикации нового результата |
| `WAIT` | Таймер текущего этапа, затем повтор этого же этапа |

Регистрация возвращает `NEXT` или `STOP`. Финализация возвращает `FINISH`, `STOP`
или `WAIT`; её `FINISH` завершает процесс. Для каждого этапа и финализации предусмотрен
свой промежуточный timer catch event. Выражение `= waitDuration` получает строку
длительности ISO 8601, например `PT1S` или `PT3S`. Неизвестное значение `route` не
имеет запасного перехода и приводит к incident. Формат выражения соответствует
[таймерам Camunda 8.10](https://docs.camunda.io/docs/components/modeler/bpmn/timer-events/).

## Повторы, пауза и отмена

Перед каждым этапом и перед новой финализацией воркер читает служебное состояние
исходной подачи в ядре. Ответ для того же `submitted_at` со статусом `SCORING`
разрешает работу. Корректный `404 NOT_FOUND`, иной статус или другая подача
останавливают оценку. Недоступность ядра либо некорректный ответ дают `WAIT` с
`waitDuration = PT1S`, без расходования попытки обязательной проверки.

Для временного сбоя проверки сохраняются три попытки: после первого сбоя ожидание
одну секунду, после второго — три секунды. Третий временный сбой готовит
`TECHNICAL_FAILURE` с `failure_kind = RETRIES_EXHAUSTED`. Постоянный сбой готовит
`TECHNICAL_FAILURE` с `failure_kind = PERMANENT`. Повторы транспортного задания
Camunda не заменяют этот счётчик бизнес-каскада.

Некорректное задание Camunda изолируется инцидентом. При неожиданном сбое воркера
или PostgreSQL задание повторяется через пять секунд без расходования попытки
проверки. Воркер получает несколько заданий одного типа и обрабатывает их
независимо, чтобы сбой одной оценки не мешал соседней.

Отмена во время уже выполняющегося внешнего вызова допускает поздний результат.
Применение в ядре сохраняет проверку статуса и исходной подачи: поздний результат
не возобновляет `CLIENT_CANCELED`. Пауза на служебном чтении также не меняет
бизнес-статус заявки.

## Сохранение и восстановление

После этапа, который получил конечный исход, сервис сохраняет подготовленный
результат в PostgreSQL. Подготовка не создаёт `AssessmentCompleted`. Задача
финализации одной транзакцией сохраняет завершённый результат и запись outbox.
Публикатор использует прежний контракт Kafka и повторяет отправку с тем же
`message_id`.

Добавочная миграция базы оценки хранит владельца экземпляра, состояние workflow и
журнал выполненных шагов. Они связывают подтверждение задания Camunda с уже
зафиксированным шагом PostgreSQL. При повторной доставке задания воркер возвращает
сохранённый исход шага; уже зафиксированные вызовы и финализация не выполняются
повторно. После сбоя между коммитом PostgreSQL и подтверждением задания процесс
продолжается по сохранённому исходу.

## Учебный запуск и обновление

Стенд использует Camunda Run **8.10.9** для Linux с включёнными Java и H2.
Дистрибутив закреплён по версии. Сервис оценки работает с REST API движка `/v2`;
отдельная клиентская SDK для Python не требуется. H2 принадлежит учебному движку,
а данные сервиса оценки остаются в PostgreSQL.

Учебная разработка и тестирование на синтетических данных допускаются бесплатно
по [условиям Self-Managed Non-Production](https://legal.camunda.com/licensing-and-other-legal-terms#self-managed-non-production-terms).
Производственный запуск требует отдельной лицензии.

Режим выбирает `LOANFLOW_ASSESSMENT_ENGINE`: по умолчанию используется `local`,
для BPMN — `camunda`. Настройки движка передаются только процессу оценки.
Окружения базы ядра и базы оценки, служебные токены и секреты остаются раздельными,
как при запуске 5.3; новые секреты для этого переключения не нужны.

Нативное исполнение BPMN проверяется на настоящих Camunda, Kafka и PostgreSQL
отдельным обязательным заданием CI. Для Compose проверяются конфигурация и сборка
образа LoanFlow с необходимыми ресурсами; сквозные сценарии выполняются без Docker.

### Запуск без Docker

Из корня репозитория загрузите закреплённый архив. Загрузчик проверяет размер и
SHA-256, распаковывает дистрибутив и печатает абсолютный путь `CAMUNDA_HOME`.
Camunda Run использует Java из своего дистрибутива.

```bash
.venv/bin/python scripts/prepare_camunda.py --cache-dir .cache/camunda-8.10.9
export CAMUNDA_HOME="$PWD/.cache/camunda-8.10.9/c8run-8.10.9"
cp services/camunda/application.yaml "$CAMUNDA_HOME/loanflow.yaml"
(cd "$CAMUNDA_HOME" && ./c8run start --no-browser --disable-connectors --config loanflow.yaml)
```

Конфигурация предназначена для локального учебного запуска и включает
уникальность `businessId` активных экземпляров. Веб-интерфейс Operate расположен
на `http://127.0.0.1:8080/operate`, учебный вход — `demo` / `demo`.
После готовности REST API на
`http://127.0.0.1:8080/v2/topology` запустите процесс оценки с окружением **базы оценки**:

```bash
LOANFLOW_ASSESSMENT_ENGINE=camunda \
LOANFLOW_CAMUNDA_URL=http://127.0.0.1:8080 \
.venv/bin/python -m services.loanflow.events assessment
```

Воркер сам разворачивает BPMN при запуске новой оценки. Отдельная команда deployment
не требуется. Перезапущенный воркер продолжает задания существующих экземпляров.
API, процесс ядра, Kafka и проверки запускаются прежними командами 5.3.
Остановка движка:

```bash
(cd "$CAMUNDA_HOME" && ./c8run stop)
```

### Запуск с Docker Compose

После подготовки `.env`, PostgreSQL, Kafka, миграций и учебного набора по README
используйте дополнительный Compose-файл при запуске прикладных сервисов:

```bash
docker compose -f compose.yaml -f compose.camunda.yaml up -d --build api abs checks worker assessment camunda
```

Overlay запускает `camunda/camunda:8.10.9`, сохраняет состояние движка в томе
`camunda_data` и передаёт настройки движка сервису `assessment`. REST API доступен
на `127.0.0.1:8080`. Последующие команды Compose для этого режима также выполняются
с обоими файлами.

### Приёмочный тест настоящего движка

Нужны ранее подготовленные Kafka 4.1.1, Java 21 для Kafka и серверные утилиты
PostgreSQL 18. `CAMUNDA_HOME` указывает на подготовленный Camunda Run. Тест создаёт
собственное окружение движка с сохраняемыми H2 и Zeebe, временный Kafka и отдельные
базы; проверка перезапуска использует то же состояние движка.
Перед прогоном остановите ручной запуск Camunda: служебная проверка самого Run
8.10.9 использует порт `9600`, поэтому он должен быть свободен. Прикладные порты
тестового движка выбираются автоматически.

```bash
CAMUNDA_HOME="$PWD/.cache/camunda-8.10.9/c8run-8.10.9" \
KAFKA_HOME=/absolute/path/kafka_2.13-4.1.1 \
JAVA_HOME=/absolute/path/jdk-21 \
PG_BINDIR=/usr/lib/postgresql/18/bin \
.venv/bin/python -m pytest -q tests/test_camunda.py --require-camunda --require-kafka
```

### Обновление с 5.3

Перед переключением с 5.3 остановите новые подачи и дождитесь завершения всех
заявок в `SCORING`. Затем остановите процесс оценки, сохраните резервную копию
базы оценки, примените добавочную миграцию, запустите движок,
после чего запустите процесс оценки с подключением к Camunda. Воркер развернёт BPMN
автоматически при создании новой оценки. Заявки в ручном
рассмотрении продолжаются через прежний API. Повторный seed, сброс Kafka offsets и
пересоздание топиков при обновлении не нужны.

Миграция с окружением **базы оценки** выполняется прежней командой:

```bash
.venv/bin/python -m services.loanflow.events migrate
```

В Compose ей соответствует `docker compose -f compose.yaml -f compose.camunda.yaml run --rm assessment-migrate`.
Существующие предложения, договоры, резервы, доказательства подписи и распоряжения
АБС продолжают использовать данные ядра; переносить их в движок не требуется.

Сохраняйте состояние H2 и Zeebe между перезапусками: в native-запуске это
`camunda-data`, в Compose — том `camunda_data`. Очистка состояния движка при
незавершённых оценках не является способом обновления. Перед обратным переключением
исполнителя также завершите текущие оценки; CLI откажет при наличии незавершённых
заданий другого режима.

## Что проверять

- Штатный каскад и ранние бизнес-отказы сохраняют порядок проверок 5.2.
- Временные сбои дают интервалы 1 и 3 секунды, а третий сбой — `RETRIES_EXHAUSTED`.
- Пауза при недоступном ядре не расходует попытки, а отмена останавливает следующий
  этап и не меняется после позднего результата.
- Повтор создания экземпляра и повтор задания не выполняют один шаг дважды.
- Перезапуск движка и воркера на таймере и после коммита шага продолжает ту же оценку.
- Финальный результат и outbox сохраняются вместе; прежние контрактные и сервисные
  регрессии подтверждают поведение ядра, подписания и АБС.
